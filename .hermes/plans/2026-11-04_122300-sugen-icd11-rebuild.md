# Sugen ICD-11 Coder Rebuild and Verification Plan

> **For Hermes:** Use this plan task-by-task with a fresh implementation context, TDD for every code change, and a review after each coherent milestone. Do not delete or modify supplied company files.

**Goal:** Build an honest, maintainable, no-key ICD-11 MMS 2026-01 coding system that satisfies Sugen’s exact Docker command, avoids development-set leakage, and is verified against the supplied scorer before any submission.

**Architecture:** Keep the supplied `public/` tree unchanged and place the implementation at the workspace root using `app/`, `tests/`, `Dockerfile`, and `docker-compose.yml`. Use a deterministic offline-first pipeline: parse JSONL, normalize the note, retrieve and rank valid MMS catalog candidates, emit up to three codes incrementally, and optionally add a separately tested API reranker only if it improves measured validation without becoming required. Development gold labels may be used by tests and analysis, never as runtime features for the submitted coder.

**Tech Stack:** Python 3.11+ standard library first; Docker Compose; pytest for tests; supplied `public/score.py`; optional HTTP API adapter only behind an explicit environment variable; Git for real history.

## 5. Risks, trade-offs, and open questions

### Risks

1. **Development-set leakage:** using gold labels in runtime would inflate the local score and damage trust. The submitted coder must load only the MMS catalog and explicitly documented static rules.
2. **Hidden generalisation distribution:** the 60 labelled notes do not represent all chapters, styles, or languages. A perfect dev score is not proof of hidden performance.
3. **Catalog titles are sparse:** title-only retrieval may miss synonyms and clinical phrasing. Add external data only after checking licensing, reproducibility, image size, and runtime constraints.
4. **API availability and cost:** optional APIs can fail through proxy, timeout, quota, or malformed output. The no-key path must remain complete and deterministic.
5. **Docker path mismatch:** changing the supplied relative layout can break the exact command. Keep the brief’s required mounts and document any generated input/output path.
6. **Time window:** the exact deadline is unknown until the original email sent timestamp is available. Do not infer it from today’s date.
7. **False confidence from local results:** only executed commands count as evidence.
8. **Audio transcription uncertainty:** the dad’s short audio was transcribed with a local tiny model; the instruction is clear enough for planning, but ask for clarification if later feedback conflicts with the transcript.

### Trade-offs

- **Standard library first:** fewer dependencies and more reliable Docker builds, at the cost of less sophisticated semantic matching.
- **Deterministic baseline before API:** easier to test and reproduce, but potentially lower hidden accuracy.
- **Optional API reranking:** may improve ambiguous notes, but adds cost, latency, proxy failure modes, and more code.
- **Small documented ruleset:** explainable and maintainable, but cannot cover every clinical synonym.
- **Frequent commits:** clearer history and easier review, but more commits to maintain.

### Open questions for Dad’s review

1. Should we permit any external medical synonym resource, or keep the solution entirely to supplied catalog plus code?
2. Should the optional API path be included, or should the submission stay deterministic and offline-first?
3. What exact email sent timestamp should be used to calculate the deadline?
4. Which hidden-score estimate, if any, is defensible after local validation?
5. Should final review artifacts include Markdown, DOCX, and PDF, with the PDF used for viewing/annotation and DOCX/Markdown for editing?
